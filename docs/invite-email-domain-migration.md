# Invite Email & Magic-Link Domain Migration

Migrate the invite-approval email so it:

1. **Sends from** `noreply@thetaletribe.com` (currently `noreply@novel-sync.com`)
2. **Uses link domain** `thetaletribe.com` (currently `story-6f89f.firebaseapp.com` / `story-6f89f.web.app`)

The approval email is generated by the Cloud Function `onInviteApproved` in
`functions/src/inviteService.ts`. It builds a Firebase Auth magic link and sends it
via AWS SES (SMTP). None of this requires code changes — only **secrets**, **env vars**,
and **console/DNS** configuration.

---

## Background: anatomy of the current link

```
https://story-6f89f.firebaseapp.com/__/auth/action      ← OUTER: Firebase Auth action handler (authDomain)
    ?apiKey=...
    &mode=signIn
    &oobCode=...
    &continueUrl=https://story-6f89f.web.app/auth/complete-signup   ← INNER: where the user lands after
    &lang=en
```

| Part | Controlled by | Change via |
|------|---------------|-----------|
| Sender `from` | `EMAIL_FROM` secret + SES verified identity | `firebase functions:secrets:set` + SES |
| Outer host `__/auth/action` | Firebase `authDomain` (`VITE_FIREBASE_AUTH_DOMAIN`) | Hosting custom domain + env var |
| Inner `continueUrl` | `MAGIC_LINK_REDIRECT_URL` secret | `firebase functions:secrets:set` |

> **Do the slow, DNS-dependent steps first** (SES domain verification, Hosting custom
> domain). They can take minutes to hours to propagate. Secrets and env vars are instant.

## Issue 1 — Send from `noreply@thetaletribe.com`

### 1.1 Verify the domain in AWS SES

The `from` address domain must be a **verified identity** in the same SES region the
SMTP host points at — `us-east-1` (`smtpHost = "email-smtp.us-east-1.amazonaws.com"` in
`functions/src/inviteService.ts:9`).

1. AWS Console → **SES** → region **US East (N. Virginia) us-east-1**.
2. **Verified identities** → **Create identity** → **Domain** → `thetaletribe.com`.
3. Enable **Easy DKIM**. SES gives you 3 CNAME records.
4. Add the CNAME records to the `thetaletribe.com` DNS zone.
5. Wait for status to flip to **Verified** (minutes–hours).

> If still in the SES sandbox, request **production access** (Transactional message type
> — auth emails are trigger-based). In sandbox you can only send to verified recipient
> addresses, so testing is limited until granted.

Recommended next: configure a **custom MAIL FROM** subdomain (step 1.1b) for SPF/DMARC
alignment and better deliverability.

### 1.1b (Recommended) Configure a custom MAIL FROM subdomain

By default SES uses `amazonses.com` as the envelope sender (`Return-Path`). SPF then
passes but does **not align** with `From: thetaletribe.com`, so DMARC's SPF check fails
(you'd be relying on DKIM alignment alone). Pointing the envelope at
`mail.thetaletribe.com` makes SPF align too → DMARC passes on both → better inbox
placement.

**Set it in SES**

1. AWS Console → **SES** (us-east-1) → **Verified identities** → click `thetaletribe.com`.
2. Tab **Custom MAIL FROM domain** → **Edit**.
3. Enter subdomain: `mail.thetaletribe.com`.
4. **Behavior on MX failure**: choose **Use default MAIL FROM domain** (safer — SES falls
   back to `amazonses.com` if your MX record breaks, so mail still sends). "Reject
   message" drops mail on failure.
5. Save. SES displays 2 DNS records.

**Add the 2 DNS records** to the `thetaletribe.com` zone (use the exact values SES shows;
the region in the MX host must match `us-east-1`):

| Type | Name | Value | Note |
|------|------|-------|------|
| MX | `mail.thetaletribe.com` | `10 feedback-smtp.us-east-1.amazonses.com` | priority 10 |
| TXT | `mail.thetaletribe.com` | `"v=spf1 include:amazonses.com ~all"` | SPF |

6. Wait for the **MAIL FROM** status to flip to **Verified** (minutes–hours).

### 1.1c (Recommended) Publish a DMARC policy

Once DKIM (1.1) and custom MAIL FROM (1.1b) are verified, add a DMARC record on the root
domain. Start in monitor-only mode, then tighten.

| Type | Name | Value |
|------|------|-------|
| TXT | `_dmarc.thetaletribe.com` | `"v=DMARC1; p=none; rua=mailto:dmarc@thetaletribe.com"` |

Roll out: `p=none` (monitor, read the aggregate `rua` reports) → `p=quarantine` →
`p=reject` once you confirm all legit mail passes alignment.

### 1.2 Update the `EMAIL_FROM` secret

```bash
firebase functions:secrets:set EMAIL_FROM
# When prompted, enter:
#   The Tale Tribe <noreply@thetaletribe.com>
```

> The display name is optional; `noreply@thetaletribe.com` alone also works. The address
> domain **must** match the SES-verified domain from step 1.1.

### 1.3 Confirm SMTP credentials cover the new domain

`SMTP_USER` / `SMTP_PASS` are SES SMTP credentials tied to an IAM identity. As long as
that identity is in the same SES account/region where `thetaletribe.com` is verified, no
change is needed. If you moved SES accounts, regenerate SMTP credentials and set:

```bash
firebase functions:secrets:set SMTP_USER
firebase functions:secrets:set SMTP_PASS
```

## Issue 2 — Use `thetaletribe.com` for the link

### 2.1 Inner `continueUrl` (the landing page) — quick

```bash
firebase functions:secrets:set MAGIC_LINK_REDIRECT_URL
# When prompted, enter:
#   https://thetaletribe.com/auth/complete-signup
```

This is read at `functions/src/inviteService.ts:69` and passed as
`actionCodeSettings.url`.

### 2.2 Outer host `__/auth/action` (the auth handler) — DNS + console

The outer host is the Firebase project `authDomain`. To serve it from
`thetaletribe.com`, that domain must be connected to **Firebase Hosting** in this project
(Hosting automatically serves the reserved `/__/auth/action` path on every connected
domain).

1. Firebase Console → **Hosting** → **Add custom domain** → `thetaletribe.com`.
2. Add the **A / TXT** records Firebase provides to the `thetaletribe.com` DNS zone.
3. Wait for the domain to show **Connected** and the SSL cert to provision.
4. Firebase Console → **Authentication** → **Settings** → **Authorized domains** →
   **Add domain** → `thetaletribe.com`.

### 2.3 Point the client at the new authDomain

`authDomain` is env-driven (`src/config/firebase.ts:11` → `VITE_FIREBASE_AUTH_DOMAIN`).
In the **production** env file:

```diff
- VITE_FIREBASE_AUTH_DOMAIN=story-6f89f.firebaseapp.com
+ VITE_FIREBASE_AUTH_DOMAIN=thetaletribe.com
```

Then rebuild + redeploy the frontend:

```bash
yarn build
firebase deploy --only hosting
```

> ⚠️ **Order guard:** finish 2.2 (steps 1–4) **before** flipping the env var. If
> `thetaletribe.com` is set as `authDomain` but not yet an Authorized Domain with a live
> Hosting cert, sign-in redirects and the magic-link handler will break.

## Deploy the functions

After updating any secrets, redeploy the affected function so it picks up new values:

```bash
firebase deploy --only functions:onInviteApproved
```

## End-to-end verification

1. Approve a test invite (set an invite doc `status` → `approved`).
2. Confirm the email arrives **from** `noreply@thetaletribe.com` (check the raw header
   `From:` and that it isn't in spam — verify DKIM/SPF pass).
3. Confirm both link hosts are `thetaletribe.com`:
   - Outer: `https://thetaletribe.com/__/auth/action?...`
   - Inner: `continueUrl=https://thetaletribe.com/auth/complete-signup`
4. Click the link → lands on `/auth/complete-signup` → complete registration succeeds
   (no "Missing or insufficient permissions"; that rule fix is already applied in
   `firestore.rules`).
